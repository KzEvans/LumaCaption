# 本地 Whisper＋MT 稳定预览实测

日期：2026-10-07。包版本 `0.1.0+5`，实现提交 `eee7aad`。原始业务计时和公开样本最终文本见 [汇总 JSON](benchmarks/whisper-mt-preview-2026-10-07.json)；旧版结果见 [0.1.0+3 基线](qwen38-whisper-mt-benchmark.md)。

## 改动与计时口径

本地 ASR 第 2 秒开始预览，随后每秒推理一次；连续两次假设一致的前缀提前送 MT，增长预览至少间隔 1.5 秒音频重译。保留最长 8 秒最终识别上下文。取消文本队列 350 ms 防抖，复用 HTTP client；改写或停止只取消相关请求，过时回调不会覆盖新原文。原文确认后用完整文本校正译文，界面明确显示“预览 · 可修订”；预览和中断译文不写入确认历史或导出。

首译是从音频输入开始到控制器接纳首个译文事件的时间，不是每个词的固定落后时间、像素绘制延迟或点击开始后的等待。模型加载和服务准备另计。首个确认译文的时间单独报告，不能用预览首译冒充确认速度。

Apple M2、16 GiB，CPU＋Accelerate，whisper.cpp 1.8.1，Metal 未启用。输入为 whisper.cpp 的公开 `samples/jfk.wav`，11 秒单声道 16 kHz，以 110 个 100 ms 帧按实时节奏输入，英语→中文，`qwen-mt-flash`。tiny 连续三轮，另补测用户当前选定的 small 一轮。没有播放音频、使用扬声器、AirPods、麦克风或系统采集；API 只接收本地识别的公开样本文字。凭据由应用从原有钥匙串读取。

## tiny 三轮结果

下表单位为秒，数值为中位数［最小–最大］。旧版在此前测得，未与新策略交错运行，因此只能描述这次观察到的改善。

| 指标 | 新版稳定预览 | 旧版仅确认原文 |
| --- | ---: | ---: |
| 首个原文 | 2.396［2.381–2.424］ | 2.484［2.324–4.774］ |
| 首个译文 | **3.609［3.583–4.046］，可修订** | 9.010［8.937–9.065］ |
| 首个确认译文 | 8.803［8.760–8.907］ | 9.124［9.041–9.188］ |
| EOF 后最后确认译文 | 0.771［0.657–0.781］ | 0.684［0.673–12.446］ |

首译中位数提前 5.401 秒，约 60%；确认首译只提前约 0.321 秒。收益主要是提前提供可修订内容，完整上下文确认时间仍接近 9 秒。新版三轮均 status=ok、110 帧、零丢弃、两条确认原文及译文。每轮记录 5 次 MT 请求，全部完成。

第一轮服务准备为 **7.070 秒**，其它两轮为 6.755、7.250 ms。第一轮从准备计时开始到首译为 10.679 秒，模型加载还在此前单独发生；异常原因未被隔离，保留该结果。tiny 模型加载分别为 742、683、696 ms。

## MT Flash 是否是主要瓶颈

15 个已记录 MT 请求，按同一会话时钟计算：

| 请求阶段 | 中位数 | 范围 |
| --- | ---: | ---: |
| 请求开始→首个译文增量 | **200.6 ms** | 177.5–619.1 ms |
| 请求开始→该请求完成 | 279.8 ms | 235.2–619.9 ms |

这些时间包含客户端、网络及服务工作，不能解释为纯模型推理。第三轮首请求的 619.1 ms 等待保留。当前记录没有失败、取消或重试，但过时工作的回调会被过滤，计时不是权威计费清单；本地服务器测试证实 client 能复用 TCP 连接，真实 API 的阶段计时不能证明每次连接确实复用。

在本次测试中，MT 通常只增加约 0.2 秒首增量等待，主要等待在提交原文前。此前旧版第三轮有原文确认后 **12.117 秒**才出现译文的异常，不能因新版三轮未复现就认为已经消除；旧报告没有 HTTP 阶段事件，无法确认异常来自模型、服务排队、网络还是客户端。

## 用户所选 small 单轮

首个原文 3.871 秒，首个 MT 请求 9.655 秒，首译 **9.892 秒**，确认首译 11.990 秒，EOF 后最终译文 2.968 秒。首次 MT 请求到首增量只有约 **237 ms**，大部分等待发生在 MT 请求之前。最后一个 3.5 秒窗口推理 2.227 秒、RTF 0.636；这是末窗口成本，不能作为全会话平均。模型加载 4.274 秒另计。

原文稳定等待、CPU 推理和排队在现有记录中无法逐项分离。small 三次 MT 请求全部完成，首增量中位数 237.0 ms，范围 188.1–365.2 ms。没有旧版 small 对照，不能把它与旧 tiny 当作版本对照。当前 small 选择保持，未用测试参数覆盖用户偏好。若优先低延迟，可以选择 tiny；若要保留较大模型，后续应验证 Metal 加速或原生流式 ASR，而不是只换 MT。

## 最终质量与代价

四轮最终英语原文对同一 22 词参考全部词序列一致，忽略大小写及标点后 WER=0%。中文均保留“美国同胞”“不要问国家能做什么”“为你”“问你能为国家做什么”四项语义，仍存在分段削弱对照关系和“你们→你”的措辞不一致。这不是总体准确率，也没有测量预览的错误率或改写频率；两次识别一致只是一种启发式判断。

提前翻译增加请求和 token；每个增长前缀重新翻译，因此可能改写已经看见的译文。重复窗口推理也增加 CPU 工作，在 small 上不能保证获得 tiny 的改善。能量阈值 VAD 对背景音乐、安静说话和噪声的处理仍有限。当前 MT 调用未传跨片段翻译记忆或术语上下文，ASR 错字会传递到译文；这也是一致性与专名处理的改进方向。

## 替代路线

以下核查了官方能力，尚未用本机测量其速度或质量，也未自动切换当前服务。

| 候选 | 适用理由 | 本应用接入与限制 |
| --- | --- | --- |
| Whisper→`qwen-mt-lite` | 官方把它定位于延迟敏感的简单翻译，支持增量流式输出 | 现有文本适配器可使用该模型 ID；需测质量、地域可用性与限流，不能据官方定位保证比本次约 0.2 秒明显更快 |
| `qwen3-asr-flash-realtime`→MT | 云端流式 ASR 有不可改写的已确认前缀和可修订后缀 | 需要新的 ASR 适配器，仍是两段处理且上传音频，不能直接替换 LiveTranslate 的模型 ID |
| Soniox `stt-rt-v5` | 一个 WebSocket 同时返回原文和句中翻译 token | 需新服务密钥和音频适配器；翻译 token 没有音频时间戳，源/译 token 不一一对应 |
| Azure 标准 Speech Translation | 提供实时原文、译文的中间与最终结果，适合双语字幕 | 需新服务配置和 SDK 适配；选择标准模式，Live Interpreter 当前不提供原文转录 |

来源：[千问 MT 选型](https://help.aliyun.com/zh/model-studio/machine-translation/)、[MT Lite 能力与限流](https://help.aliyun.com/zh/model-studio/qwen-mt-lite)、[Qwen ASR 实时事件](https://help.aliyun.com/zh/model-studio/qwen-asr-realtime-server-events)、[Soniox 实时翻译](https://soniox.com/docs/translation/stt-translation/rt-translation)、[Azure Speech Translation](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/speech-translation)。

现有 LiveTranslate 路线的主要限制是上传音频、依赖网络与服务端分段；当前应用原文与译文还可能显示成分开的行，尚未充分利用关联信息配对。现有本地路线保护原始音频，但 CPU、ASR 稳定性、串行 ASR→MT、预览改写和跨片段上下文都是瓶颈。单一干净短样本无法判断长对话、噪声、专名或不同网络下谁更准确。
